# Kite 路线图

> 这是**判断依据**，不是承诺。每条都写了「为什么做 / 为什么不做」，方便你反对我。

## 原则

1. **端上优先** —— 能在这台手机上做完的，不引入服务器。
2. **不引依赖** —— 现有 11 个运行时依赖已经不少了。能用 JDK / Android SDK 写就不加库。
3. **能力换风险，交给用户选** —— 不给「默认全开」，但给「你自己开」。
4. **许可证要干净** —— LGPL / GPL 的代码不引入（见 [THIRD-PARTY.md](../THIRD-PARTY.md)）。
5. **不骗人** —— 做不到的事情写在文档里，不藏在 README 角落。

## 近期（0.2.x）

### 语音唤醒与连续对话

**为什么**：现在长按麦克风只能说一句，说完就断。真正常用的场景是「一边做事一边说」。
**怎么做**：`ContinuousVoice.kt` 已经有骨架（连续识别循环），缺唤醒词。唤醒词用本地
`Porcupine` 或 `sherpa-onnx` 关键词检测，不上传音频。
**风险**：常驻麦克风耗电，必须做成可选 + 前台服务可见。

### MCP OAuth

**为什么**：现在只能填 Header Token，接 GitHub / Linear / Notion 这类官方 MCP 服务器要手动造 token，且会过期。
**怎么做**：RFC 6749 授权码 + PKCE，`CustomTabsIntent` 打开授权页，回调走 deep link。
**风险**：回调 URI 注册要改 Manifest，注意别让 Play 版多出可疑 intent-filter。

### 浏览器增强

**为什么**：现在只能读文本和点击，遇到需要下载文件、或者多步骤跨页面操作就断了。
**怎么做**：`WebView` 截图（`Bitmap` 转 base64 给视觉模型）、下载交给系统 `DownloadManager`、多标签用 `WebView` 池。
**风险**：截图会进上下文，token 消耗大，要限尺寸。

### 代码 diff 预览

**为什么**：模型改文件后，用户只看到「已写入」，不知道改了什么。这是信任问题。
**怎么做**：`write_file` / `replace_in_file` 前保存旧内容（`UndoStore` 已经存了），UI 里做行级 diff。
**风险**：无。

### 多工作区

**为什么**：现在只有一个工作区，切项目要改设置。
**怎么做**：`Settings` 存工作区列表 + 当前选中项，UI 加切换器。
**风险**：路径隔离逻辑要跟着改，别改出穿越漏洞。

## 中期（0.3.x – 0.5.x）

### 迁移到官方 MCP Kotlin SDK

**为什么**：`mcp/McpClient.kt` 是自己写的，只覆盖了 tools/resources/prompts，没有 OAuth、
没有重连退避、没有 stdio。官方 SDK 都有。
**为什么不急**：官方 Kotlin SDK 还在演进，API 可能变。等它稳定再迁。
**迁移成本**：`McpClient` / `McpManager` 整体替换，`McpModels.kt` 大概率能留。

### 音视频转写

**为什么**：现在发个语音条、录个会议，Kite 完全看不懂。
**怎么做**：两条路 —— 本地 `whisper.cpp`（体积大、慢、但隐私好），或云端 ASR（快、要 Key）。
默认本地，允许切云端。
**风险**：`whisper.cpp` 的 Android 集成要带 native so，APK 会大 20–50 MB。可能做成可选下载。

### 多语言

**为什么**：现在全中文硬编码在 `strings.xml` 和 Kotlin 里。
**怎么做**：先把散落的硬编码文案收进 `strings.xml`，再加 `values-en/`。
**风险**：`Prompts.kt` 的系统提示词也要双语，不然英文界面配中文提示词很怪。

### 技能市场

**为什么**：`Skills.kt` 已经能从 `.kite/skills/` 读技能了，但没有分享渠道。
**怎么做**：先做导入导出（zip / 单文件 URL），市场以后再说 —— 市场需要服务端，违反原则 1。
**风险**：技能里可以写任意指令，导入时必须让用户先看内容再确认。

## 长期（1.0+）

### 多端轻客户端

微信小程序 + 鸿蒙元服务，做「Gateway 驱动的轻助手」。完整方案见 [PLATFORM-PLAN.md](PLATFORM-PLAN.md)。

**为什么**：手机端能力最强但只能自己用；小程序/元服务能分享给别人。
**为什么慢**：这两端都不能直连模型（Key 会泄漏），必须有个 Gateway 服务端 —— 而 Kite 现在是**零服务端**的。
这等于要新起一个项目。
**结论**：等 Android 端稳定了再说，不着急。

### 可选 Gateway

让原生端也能切到「服务端持 Key」模式，方便多设备共享配额。
**风险**：一旦有服务端，隐私承诺就要重写。会做成**纯可选、默认关闭**。

## 明确不做

写在这里，免得反复讨论：

| 不做 | 原因 |
|---|---|
| **内置 root 绕过 / 漏洞利用** | 违法风险，且刷坏设备不可逆。Kite 只调用系统已有能力。 |
| **后台虚拟屏幕（非 root）** | 需要 `ADD_TRUSTED_DISPLAY` 系统签名权限，拿不到。除非 root，做不到就是做不到。 |
| **云同步 / 账号体系** | 违反隐私承诺。想同步请自己用 Syncthing 或 Git 同步工作区。 |
| **广告 / 内购 / 统计 SDK** | 同上。 |
| **内置模型推理** | 手机跑不动有意义的模型，且 APK 会大到离谱。BYOK 是更好的形态。 |
| **Termux 式终端界面** | Kite 是 Agent，不是 shell。Shell 是它**调用**的工具，不是它的界面。 |
| **把 Operit / Mika 代码搬进来** | Operit 是 LGPL，搬进来整个项目就得换许可证。Mika 虽然 Apache-2.0，但独立实现更干净。 |
| **Play 版带敏感权限** | 短信、通话记录、所有文件访问这些只存在于个人版。Play 版必须干净。 |
